# Deep Audit — 对抗式全项目审计

固化自 GIS7/AIWatch 历史审计（commits 778fa87、028a8ea 及 2026-07-04 稳定性审计）。核心原则：**未经红队复核的发现不许汇报，未经用户拍板不许动手修。**

## 流程

1. **定范围**：需求符合性（对照需求文档→用 spec-trace skill）还是工程健康（bug/性能/稳定性）？都要就分两轮，先健康后符合性。
2. **并行对抗审查**——派 3~5 个子代理，各带独立敌对视角：
   - 静默失败猎手：吞错 catch、假成功弹窗、`toDouble()` 默认 0、catch-all 降级伪装成"无数据"
   - 数据完整性：事务无 rollback、commit 失败继续走、单位换算、列错位、缺失值被伪造
   - 需求对照：规格逐条 vs 代码，输出追溯矩阵（需求→文件:行→测试→✅/⚠/❌）
   - （C++ 加）内存/生命周期：UAF、事务内 processEvents、悬空 this、静态析构顺序
   - （线上服务加）稳定性：游标/断档、健康检查盲区、告警缺口
3. **红队复核（必做）**：再派一个代理对全部发现逐条回代码求证，标【通过/驳回/修正】。历史首轮误报率 20~30%（例：游标 max(publishedAt) 修法被红队证明比原实现更错）。
4. **输出**：CRITICAL/HIGH/MEDIUM/LOW 排序；每条 = 文件:行 + 具体触发场景 + 最小修法。**需用户拍板的业务口径单列一节**，不与 bug 混排。
5. **停**。汇报即交付。用户说修才修，修完逐条标 fixed/skipped 再复验。

## 红线

| 借口 | 现实 |
|---|---|
| "发现了就顺手修掉" | 审计交付物是报告+拍板点。先报告。 |
| "这条很明显，不用复核" | 误报率 20~30%。全部复核。 |
| "缺数据补个默认值" | 缺失填 N/A + Remark。伪造 = 最恶劣失败。 |
| "大体都实现了" | 逐条打钩。部分实现标 ⚠ 并写缺什么。 |
