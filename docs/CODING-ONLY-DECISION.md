# 移除生态捆绑：配置层的实际边界

日期：2026-10-27。产品：本机 WorkBuddy AI 5.8.4。状态：用户已批准独立工程版及“原厂更新后运行一次”的生成脚本；原厂安装保留。

用户最新目标是移除无用的生态内容、集中提升代码能力；同时，先前确认的 v3 选择是只改配置层，设计冲突先确认。这两条约束共同决定后续步骤。

## 真实对照

1. 16:25 安装 v4 配置及 `.codebuddy/settings.local.json`；20:37 重启后建立会话 `42156208-e06c-4f6a-84d1-8c9ae3f984ec`，工作区为 harness。
2. 日志 `PluginsProductProvider.provide` 显示 14 个活动插件，包含办公、支付、设计和会议。`sheet-agent` 实际成功派发。模型列出 33 个技能。工作区文件中 47 个 false 不能证明运行时禁用成功。
3. 20:41 桌面启动后再次 apply，全局 47 项为 false。新会话 `ae70f25b-c9d1-4edc-8df3-efa0d4d02dd6` 缩到 6 个活动插件，`sheet-agent` 真实拒绝，但 tmeet 仍活动，且模型仍看到内置生态技能。

原始证据保存在本机 `runtime-probe/v4/report.md`、两个会话 transcript、对应 PID 7564 / 19416 的 harness 日志；不将带凭据的完整日志提交到公开仓库。

## 已确认的三处原因

- 桌面 `main/server.js` 的 `restoreBuiltinExtensionOverrides` 每次启动删除全局内置插件禁用值和内置技能 off 值。
- 桌面把账号启用项并入会话设置，再以 CLI 设置传给引擎。引擎 `getEnabledPlugins()` 按 user → project → project-local → CLI → session 合并，所以工作区覆盖无法胜过 CLI。
- 引擎 `resolveSkillOverrideState()` 对插件技能直接返回 on。单独给会议插件技能写 off 并不能可靠禁用它。

## 已批准并实现的后续改动

保留配置 profile 路线，通过 `build` 明确选择独立工程版程序副本：

1. 在副本的 `restoreBuiltinExtensionOverrides` 保留用户显式禁用值。早期本机候选是两个精确替换；当前 `scripts/engineering.py` 统一处理程序副本和配置，不发布厂商程序文件。
2. 账号启用项与用户设置合并时，显式 false 优先，避免 tmeet 被账号重新打开；仍保留账号权限和订阅校验。
3. 使用工程 profile 的工具列表与技能开关，去掉办公、金融、支付、推广、生态管理及无关多媒体注入；保留代码读写、搜索、终端、调试、浏览器测试和代码代理。
4. 单独核查首页入口的实现，能移除的生态入口在副本中移除；界面验收与运行能力验收分开记录。

5. 关闭工程副本自己的静默更新、下载及安装入口，避免下一次启动被 NSIS 覆盖。原厂更新能力保留；更新后再次运行生成器。
6. 生成器检查源码锚点、ASAR 条目/块摘要、EXE 资源中的 ASAR 摘要及 JavaScript 语法；相同源与 profile 校验后复用产物。生成配置前要求所有 WorkBuddy 实例退出，避免旧内存状态回写。

用户确认原文要点：“写一个专门的一次性配置脚本……每次更新完以后我运行它……替换配置，生成独立的工程补丁……在这一个版本持久永久地生效。”

后续验收分别证明界面、模型 system 输入、语法反馈、代码断言、插件加载及反向调用，不把隐藏按钮或绿色静态检查代替实际运行证据。未来未知版本的内部结构变化仍需适配，不声称无限版本兼容。
